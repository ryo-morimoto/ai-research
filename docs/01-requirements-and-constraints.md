## 0. やりたいこと

**調査にかかる時間を短くする。そのために、時間を食っている原因を取り除くシステムを作る。**

**どの機械から依頼しても、どの会話・どの作業場所から依頼しても、同じ依頼には同じ結果が同じ速さで返ってくる。** これは速さの前提でもある。

- 機械ごとに記憶が違えば、別の機械では調べ直しになる。
- 会話の文脈を調査の一歩ごとに運ぶと、その分だけ1ステップが重くなり、キャッシュも効きにくい。
- 関係のない文脈に引きずられると、結果の質も落ちる。

ここでいう「同じ」は、**利用者が機械や会話の違いを意識しなくてよい**という意味である。LLM に送る文字列が完全に一致することまでは求めない（§1.3）。

**論文・研究の知見を問う調査は、一次資料（論文の書誌と抄録、読めれば本文）まで届く。** 解説記事や百科事典は、一次資料の代わりにしない。

**調べものは、利用者が道具を指定しなくても、このシステムの経路を通る。** 速さ（再利用）・確かさ（照合）・一貫性・外部への配慮は、どれもこの経路の上でしか保証できない。経路を通らなかった結果は、それと分かるようにする。

### 0.1 成功の物差し

| 物差し | 目標 | 現状（ボトルネック分析より） |
|---|---|---|
| 依頼から最初の結果が届くまで | 60秒以内（P95） | その場検索で約5分、並列調査で25〜60分超 |
| 最初の結果から続きが届くまで | 180秒以内（P95） | 同上 |
| 作り直し・調べ直しに使った時間の割合 | 下がり続けること | 作り直し6件、同じテーマの重複調査5系統（直近10日） |
| 何も進んでいない時間の割合 | 下がり続けること | 並列調査で「残りの調査待ち」が5回続いた例あり |
| 依頼した機械による結果の違い | 0件 | 未計測 |
| 依頼した会話・作業場所による結果の違い | 0件 | 未計測 |

- 時刻の起点は、利用者が依頼を送った時点
- 「結果の違い」の数え方は §1.3 に定める

### 0.2 範囲

- 使う人：利用者本人（まずは1人）
- 使う機械：利用者が依頼に使う機械すべて（複数の PC）
- 依頼する場所：どの会話からでも、どの作業ディレクトリ・プロジェクトからでも。面としては次のすべて

  | 面 | 例 |
  |---|---|
  | Claude Code | 各 PC のターミナル、デスクトップアプリの Code、クラウドのセッション |
  | Claude のチャット | ブラウザ、デスクトップアプリの Chat、スマートフォンのアプリ |
- 対象：Claude Code などの AI エージェントで行う調査。新しい概念の調査と、既に調べたテーマの再調査の両方

### 0.3 やらないこと

- 出典そのものの誤りを見抜くこと（出典を示して、利用者が気づけるようにはする）
- 成果物の後工程（スキル化、長いレポート化）を速くすること。これは依頼の分け方の問題として扱う
- 複数人での共有。使う人は1人のまま

## 1. 制約の分け方

### 1.1 減らすもの：調査の時間を3つに分ける

依頼から結果までの時間は、どの瞬間を取っても次の3つのどれか1つに当たる。

| 区分 | 定義 | 該当する原因 |
|---|---|---|
| **W 無駄な作業** | 結果に使われない作業をしている時間 | 外れた前提での作り直し / 前に調べたことの調べ直し（別の機械で調べたものを含む） / 依頼に対して深すぎる調査 |
| **S 必要な作業の遅さ** | 結果に使われる作業を、必要以上に遅くやっている時間 | 思考量の過多 / キャッシュの効かない読み直し / 要約を挟む遅い取得経路 / ツール出力の肥大で1ステップが重くなる / 調査に関係のない会話の文脈を毎ステップ運ぶ |
| **P 停滞** | 何も進んでいない時間 | 一番遅い作業の完了待ち / 承認待ち / 取れない出典のタイムアウトと再試行 / 利用者の返事待ち |

### 1.2 守るもの

| 区分 | 相手 |
|---|---|
| **Q 結果の確かさと一貫性** | 結果そのもの |
| **U 利用者の負担** | 利用者 |
| **E 外部への影響** | 出典、外部サービス、第三者 |
| **R 資源** | 費用、計算資源 |

### 1.3 「結果が同じ」の定義

結果は、主張・出典・確認状態の組で比べる。次の違いだけは「違い」に数えない。どれも結果の上に理由が表示されることを条件とする。

1. 出典そのものが変わった（取り直した結果、内容が更新されていた）
2. 時間の打ち切りで、確認が済まなかった（Q-04 で示される）
3. モデルの出力の揺らぎ（同じ依頼でも、検索語や主張の言い回しが毎回少し違う）。会話で使うモデル（Opus / Sonnet など）の違いによる差もここに含める

3 は避けられないので、揺らぎの大きさは別に測る（§5）。モデルの違いを含めてよいのは、台帳に入るのが原文の抜き書きだけで、モデルが違っても持ち込まれる事実は変わらないからである（Q-03）。

## 2. 制約の宣言

「強さ」は MUST（破れば不合格）/ SHOULD（原則守る。外すなら理由を残す）/ MUST NOT（してはならない）。

### 2.1 減らすもの

#### W 無駄な作業

| ID | 強さ | 制約 | 根拠（もとの要件） | 確かめ方 |
|---|---|---|---|---|
| W-01 | MUST | 依頼から60秒以内に、向きが合っているかを利用者が確かめられる最初の結果を出す | 作り直しの最大の原因は、外れた前提で長い成果物を書き切ったこと（ボトルネック分析 1） | 依頼から最初の結果までを計測 |
| W-02 | MUST | 利用者が途中で向きを変えたら、以降の作業に反映し、外れた作業を続けない | 調査中の範囲変更に対応した例（NixOS の回） | 途中で指示を変える試験 |
| W-03 | MUST | 以前に確かめた事実は、出典が変わっていなければ、読み直しに時間を使わない。どの機械・どの会話で確かめた事実でも同じ | 同じテーマを複数セッションで調べ直していた（ボトルネック分析 2）。別の機械で調べたことも調べ直していた（10/24） | 機械Aで1回目、機械Bで2回目に同じ依頼。2回目で、変わっていない出典の再読込時間が0に近いか |
| W-04 | MUST | 最初の結果と続き（合計4分）を超える調査は、利用者が求めたときだけ行う | どの依頼にも重い手順を回していた（ボトルネック分析 3） | 求めていない深掘りが起きないか |

#### S 必要な作業の遅さ

| ID | 強さ | 制約 | 根拠（もとの要件） | 確かめ方 |
|---|---|---|---|---|
| S-01 | MUST | 調査が長くなっても、1ステップあたりの時間が増え続けない | 巨大なツール出力は文脈に残り、以後すべてのターンを重くする（適用手順書 フェーズ5） | ステップ数に対する1ステップの時間の推移 |
| S-02 | MUST | 休憩やセッションの区切りを挟んでも、作業の再開が大きく遅くならない | 10分以上空くとキャッシュのヒット率が0〜5%まで落ち、全体の読み直しになる（適用手順書 フェーズ2） | 休憩を挟んだ再開時の最初の応答時間 |
| S-03 | MUST | 出典の原文を得る時間は、取得経路を選べるなら最も速いものを使った場合に近い | GitHub は raw 取得0.43秒・浅い clone 1.1秒。要約を挟む取得は遅く、原文も得られない（手元の計測） | 出典種別ごとの取得時間 |
| S-04 | SHOULD | 依頼の難しさに対して、思考量を過大にしない | 最初の出力までの時間は思考量で大きく変わる（適用手順書 フェーズ3） | 依頼の種類ごとの応答開始時間 |
| S-05 | MUST | **調査のために会話の側で回るターン数と、そこへ流し込む量が、会話の長さや作業場所によって増えない。** 長い会話と新しい会話で、最初の結果までの時間の差は10秒以内【値は要計測】 | 会話の文脈を調査の一歩ごとに運ぶと、その分だけ1ステップが重くなり、キャッシュも効きにくい（10/24） | 長い会話（目安15万トークン）の途中と新しい会話の冒頭、別々のプロジェクトから同じ依頼を出し、最初の結果までの時間と、調査に使ったターン数を比べる |
| S-06 | MUST | **調査のために会話に流し込む量は、問いに関係するものと、道具を使うのに要る最小の説明だけにする。** 同じ説明を複数の場所から読ませない | 1つの事実を問う依頼で、会話に入った段落のうち根拠に使われたのは 5〜18% だった。手順の説明が、アカウントの指示・スキル・道具の説明文の3か所に重なっていた（10/24） | 依頼セットで、会話に入った推定トークンと、根拠に使われた段落の割合（精度）を測る。目標は §2.5 |

#### P 停滞

| ID | 強さ | 制約 | 根拠（もとの要件） | 確かめ方 |
|---|---|---|---|---|
| P-01 | MUST | 並行する作業のうち遅いものが、他の結果の提示を止めない | 並列調査は一番遅い作業に全体が引きずられていた（ボトルネック分析 3） | 1つの作業を人為的に遅らせた試験 |
| P-02 | MUST | 取れない出典は時間上限で打ち切り、取れなかったことを結果に示す。同じ失敗を同じ調査の中で繰り返さない | 共有リンクや動画の字幕で数往復を使っていた（ボトルネック分析 5） | 取得不能な出典を含む試験 |
| P-03 | MUST | 読み取りだけの操作で、利用者の承認待ちのために止まらない | 承認待ちは人間の待ち時間になる（適用手順書 フェーズ4） | 調査中の承認待ちの回数 |
| P-04 | MUST | 利用者に確かめたいことは結果と一緒に出し、返事を待って作業を止めない | 問いだけ出して待つと、その間は何も進まない | 質問を含む回で、作業が止まった時間 |
| P-05 | MUST | **システムの側の失敗は、再試行してよいか、どこまで進んだか、次に何をすればよいかと一緒に返す。** 内部の事情だけを返さない | ハブのストレージの時間切れで、内部のエラー文だけが返り、再試行も続きの受け取りもできなかった（10/24） | 失敗を起こす試験で、返る値に種別・再試行の可否・次の手があるか |
| P-06 | MUST | **集める作業が残っていないときは、続きを待たせずに終わったと分かる。何も返せなかったときは、理由（検索で見つからない／見つけたが取れない／検索していない）が分かる** | 続きが空のまま4分間終わらず、15〜20秒の待ちが空振りした。0件の結果に理由がなかった（10/25） | 作業が早く尽きる試験で、done になるまでの時間。0件になる試験で、理由があるか |
| P-07 | MUST | **取得できた出典は、問いに合う段落が選ばれなくても行き止まりにしない。** そうなったことが結果で分かり、その出典の中を探すか、経路の外で読める | 取得はできたが関連段落が返らなかったページが、結果にも打ち切りにも出ず、組み込みの取得も止められた（10/26） | 段落が選ばれない出典を含む試験で、結果に出るか、探せるか |

### 2.2 守るもの

#### Q 結果の確かさと一貫性

| ID | 強さ | 制約 | 根拠（もとの要件） | 確かめ方 |
|---|---|---|---|---|
| Q-01 | MUST | 主張ごとに、出典と照合の状態が分かる。照合の状態は「引用が原文にあるか」だけを表し、主張がその引用から正しく導かれるかは表さないことが、名前から分かる。出典の種類（一次：論文・公式文書／二次：百科事典・解説／その他）が分かる。台帳から持ち込んだ事実は、確かめた日時も分かる。**結果に書くラベル（照合できたもの・書誌だけ確かめたもの・照合していないもの・背景知識・経路外）の一覧は1か所で決め、どの会話・どの担当も同じラベルを使う** | 生成検索の引用は、文の約半数しか完全には支えていない（Liu et al. 2023） | 全主張に出典と確認状態があるか |
| Q-02 | MUST | 以前の調査から持ち込んだ事実を使った結果は、その場で出典を取り直した場合と同じになる | 持ち込みで速くしても、確かさは落とさない | 出典を書き換えた試験で、古い事実が確認済として出ないか |
| Q-03 | MUST NOT | システムが作った文（要約、解釈、結論）を、次の調査の根拠として持ち込まない | LLM が書いた抽象化を残すと誤りが再生産され、正答率が最大28ポイント下がった（arXiv 2610.27406、preprint） | 持ち込み対象に、出典にない文が1件もないか |
| Q-04 | MUST | 取れなかった出典（確定した喪失）のうち、答えに影響したもの（利用者が示した出典、答えに使った出典の照らし直し）は1件ずつ分かる。それ以外は件数で分かり、URL も分かる（経路外で読むため）。**まだ集めている作業は、取れなかったものと区別して示す**（進行中を喪失として報告させない） | 速さと引き換えに抜けた部分を、利用者が見落とさないため。ただし関係のない取得失敗を1件ずつ説明すると、答えより長くなった（10/24） | 打ち切りを起こした試験 |
| Q-05 | MUST | **持ち込める事実、調査の手順、道具とその版、出典を取得する条件（取得元・頻度制限）が、機械ごとに分かれていない。** 利用者は、どの機械から依頼したかを意識しなくてよい | 機械ごとに記憶や設定が違うと、どこで動かしたかで結果が変わり、使う側がそれを意識しなければならない（10/24）。ai-memory も、機械をまたいで同じ記憶を使えることを中心の機能にしている | 2台から同じ依頼を出し、§1.3 の定義で結果を比べる。あわせて、事実・手順・道具・取得条件のうち機械ごとに持っているものが無いかを棚卸しする |
| Q-06 | MUST | **会話の文脈や作業場所の設定に由来する内容を、調査で確かめた事実として保存したり、次の調査に持ち込んだりしない。** 会話を参照して依頼の意味を補ったときは、補った後の問い（解釈した問い）を最初の結果に示す | 調査で得た事実を事前の文脈で上書きし、事実として保存した事例がある（10/24）。「それをもっと」のように、会話を参照しないと意味が決まらない依頼もあるので、補うこと自体は許す。ただし利用者が確かめられる形で見せる | 会話に調査結果と矛盾する前提を置いた状態で依頼し、保存された事実に出典の原文にないものが1件もないかを照合する（上書き試験）。長い会話の途中、新しい会話、別々のプロジェクトから同じ解釈になる依頼を出し、結果を §1.3 の定義で比べる |
| Q-07 | MUST | **システムの経路を通らずに得た内容（組み込みのウェブ検索など）は、結果の上でそれと分かり、通らなかった理由が示される。** 確認済の印は付かず、台帳にも入らない | 経路の外の結果は照合も再利用もされない。利用者が区別できなければ、確かめた事実と同じに扱ってしまう | 経路の外に落とした試験（明示の指定、システムに届かない状態）で、結果に表示と理由があるか。台帳が増えていないか |
| Q-08 | MUST | **論文・研究の知見を問う調査では、一次資料（論文の書誌：著者・年・誌名・DOI と、抄録。公開の版や PDF が読めれば本文）に届く。** 届かなかった一次資料は、DOI か URL と理由が分かる | 文献調査で、出版社のページが毎回取得を拒み（5件中4件が blocked など）、根拠の過半が解説記事・百科事典になった。書誌も本文から推測するしかなかった（10/25） | 学術の依頼セット（bench/cases/scholarly-2026-10-25.json）で、一次資料の出典に届いた割合。目標は §2.5 |

### 2.3 費用の上限の決め方（R-01）

v0.3 から変えない。

既存の調査エージェント（Jina node-DeepResearch、gpt-researcher、open_deep_research）の1回あたりの消費をもとに、次のように決めた。

| 段階 | 上限 | 対応づけた既存の値 |
|---|---|---|
| 最初の結果（60秒） | 10万トークン | Jina の effort low |
| 続きまでの合計（4分） | 60万トークン | Jina の effort medium と open_deep_research の gpt-4.1 設定の間 |
| 依頼時の深掘り（合計） | 140万トークン | open_deep_research の Claude Sonnet 4 設定 |

- キャッシュから読んだ分を数えない理由【推論】：長い会話から依頼すると、会話の前置きの読み直しだけで上限に届いてしまう。キャッシュ読み出しは料金も1割程度なので、暴走の目安には向かない。
- サブスクリプションの利用枠で使う場合は、金額ではなく利用枠の消費として効く。トークン数の上限はそのまま使える。

## 4. 制約どうしの緊張関係

| 緊張 | 優先 |
|---|---|
| 60秒で最初の結果（W-01）と、確認済の主張を出すこと（Q-01） | 60秒を優先。間に合わない主張は「未確認」として出す |
| 再利用で速くする（W-03）と、その場で取り直した場合と同じ結果（Q-02） | Q-02 を優先。照らし直しが間に合わなければ「未確認」として出す |
| 抜き書きを短くする（E-01）と、照らし直しの頑健さ | E-01 を優先。短い抜き書きで成り立つ手段を選ぶ |
| 記憶を1か所に寄せる（Q-05）と、常駐サーバーを持たないこと（R-02） | Q-05 を優先。保守の要らないマネージドな置き場所を選べば両立する |
| 記憶を1か所に寄せる（Q-05）と、置き場所に届かないときにも調査すること | 調査は止めない。ただし持ち込みを使わず、すべて「未確認」とし、「共有の記憶に届かなかった」と結果に示す。このとき確かめた事実は、届くようになったら共有の記憶に入れる |
| 会話を参照して依頼を補う（W-02・会話を参照する依頼）と、文脈由来の内容を事実にしない（Q-06） | 補ってよい。補った結果は「解釈した問い」として最初の結果に示し、違っていれば W-02 で直す。保存・持ち込みは出典の原文に限るので、補った内容が事実として残ることはない |
| システムの経路に乗せる（U-03）と、利用者が別の道具を明示したとき | 利用者の明示を優先する。経路の外で調べ、Q-07 で示す |
| システムの経路に乗せる（U-03）と、システムに届かないときにも調査すること | 調査は止めない。経路の外で調べ、Q-07 で示す。経路の外の道具を止める仕組みは、システムに届かないときには止めない側に倒れる（止めたままにしない） |
| 記憶を1か所で共有する（Q-05）と、別の話題の事実が混ざる | 話題の区切り（名前空間）は作らない。問いとの関連の下限で、関係のない候補を出さない（S-06）。利用者の判断（10/25） |
| 一次資料に届く（Q-08）と、取得先の規約と頻度制限（E-02） | 出版社のページは取得を拒むので、規約が許す書誌・抄録の API（キー不要のものから）を使う。本文は、利用者が読める公開の版（PMC など）があるときだけ |
| 流し込む量を減らす（S-06）と、打ち切りを示す（Q-04） | 答えに影響したものは1件ずつ、それ以外は件数で示す（Q-04 の書き方） |
| 往復と形式を軽くする（U-04）と、確認状態を示す（Q-01）・解釈した問いを示す（Q-06） | 確認状態は出典の後ろに短く付ける。解釈した問いは、会話から補ったときだけ示す（Q-06 の書き方どおり） |
| 経路率を上げる（U-03）と、利用者の負担を増やさない（U-01） | U-01 を優先。経路に乗せる仕組みは、アカウントへの1回の登録で全面に届くものだけにする。面ごと・機械ごとの設定が要る仕組みは採らない |
| 利用者の好みや作業中のプロジェクトに合わせたいとき（Q-06） | 常に効かせたい方針（例：アフィリエイト・SEO 目的のサイトを除く）は、どの機械・会話でも同じに効く場所に置く。その場の好みは、依頼文か解釈した問いに書かれたときだけ使う |

### 捨てた案

| 案 | 捨てた理由 |
|---|---|
| 調査を会話の外の固定した実行環境（版を固定したコンテナ内の headless の Claude Code）で動かし、依頼文と解釈した問いだけを渡す（v0.3 別紙） | v0.3 の Q-05・Q-06 を「LLM に送る本文が同じ」と読んだことから必要になった案だった。もとの要件（記憶・手順・道具が機械ごとに分かれていない、文脈に引きずられない）には過剰で、各機械への導入物とスマートフォンから使えない制限を生んだ |
| 記憶を各機械に持ち、追記のみの記録を同期する | 同期の遅れで機械ごとに持ち込める事実が違う状態が生じる。1か所に寄せる案で R-02 も満たせるので不要 |
| 道具の説明文を強くするだけで、経路に乗せる（v0.5 時点の運用） | 説明文が読み込まれた会話でも、組み込みのウェブ検索が使われた（10/24）。道具が遅延読み込みのときは説明文そのものが読まれない |
| 組み込みのウェブ検索を設定で一律に禁止する | システムに届かないときに調査が止まる（U-03 の例外、§4）。チャットには禁止する設定がない |
| 機械ごとに設定ファイル・スクリプトを入れて経路に乗せる | U-01 に反する。機械ごとに版がずれ、Q-05 にも反する |
